## 3. 明确「未修」的项（需要架构/流程决策，不是补丁）

| # | 项 | 为什么不在本轮修 | 建议 |
|---|---|---|---|
| 1 | **Go 引擎 + 独立进程 + AST 白名单** | 主项目语言选型已定 Go，重写不是「修复」；MVP 的冻结只是应急 | 冻结 v0.10 为 oracle，按 `protocol / engine / scoring / io` 四层重写 |
| 2 | **512² 地图** | 触碰协议编码、视野性能、回放体积三处，且要重标定全部数值 | 先做 map 编码（RLE/base64）与视野增量，再用 8–10 seed 重跑平衡 |
| 3 | **协议与引擎分层** | `rules.js` 1769 行拆 4 个模块属大重构，风险高于收益（马上要换 Go） | 在 Go 侧直接按目标分层实现，不要照搬 JS 结构 |
| 4 | **版本控制策略（外层仓库无代码）** | 外层 `.gitignore` 显式忽略 `/MVP/`，是用户既定策略，不能擅自改 | 二选一：① 把 MVP 纳入外层仓库；② 给 MVP 独立仓库配远端备份。**需要你决定** |
| 5 | **BT/Elo 排名、选手包哈希、社区 PR 流水线** | 属正式赛功能，原型阶段无意义 | 与 Go 引擎同批做 |
| 6 | **跨语言确定性（golden trace）** | 需要先在 Go 侧有可运行的协议层 | 先固化规范化序列化规范，再产 3–5 组 trace 对拍 |
| 7 | **渲染层覆盖率** | `match.js` 由 `vm` 加载，V8 采不到；写 DOM 快照比对成本高 | 用 Playwright 截图比对，或在 Go/前端重构后统一做 |

## 4. 残留风险（已写进 README「已知问题」）

1. **冻结不是安全边界**：同进程 Bot 仍可通过 `require`、全局、CPU 耗尽等方式干扰；比赛前必须换进程模型；
2. **`rulesHash` 覆盖整张规则表**：任何数值微调都会拒绝所有旧 Bot，赛前需要「赛季规则包」策略；
3. **`match.js` 只有 smoke 级验证**：Canvas 调用计数能发现「没画」，发现不了「画错位置」；
4. **`hello` 体积已到 29.9 KB**：离 64 KB 上限只剩一倍余量，任何地图字段扩展都要先算体积。
