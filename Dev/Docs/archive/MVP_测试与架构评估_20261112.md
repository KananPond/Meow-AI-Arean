### 2.2 `npm run coverage` / `npm run ci` —— 实为红态

在无并发的干净重跑下 `npm run coverage` **稳定失败（exit 1）**，输出只有：

```
PASS  弹道物理 / 伤害模型 / 弹种    2264ms  BALLISTICS_TESTS_OK
测试未通过，覆盖率无意义
```

**根因（已实测确认）**：`scripts/coverage.js:38` 给 `spawnSync('test/all.js')` 设了 `timeout: 300000`（5 分钟），而 `NODE_V8_COVERAGE` 插桩代价极高——实测单个 `test/rules_test.js` 从 **14,288 ms 膨胀到 183,212 ms（12.8×）**；全套 10 个套件插桩后远超 300 s。超时后 `status === null`，`:42` 一律打印「测试未通过，覆盖率无意义」并 `exit(1)`。

这条报错**具有误导性**：测试其实通过了，失败的是覆盖率采集进程。由于 `package.json:20` 的 `ci = check && test && coverage`，**整个 CI 门禁目前是红的**；README 与 `MVP_修复报告_v0.10.md` 宣称的「`COVERAGE_OK`」在当前 256² 快照下已不成立。

## 3. 覆盖范围与有效性

### 3.1 断言口径（已实跑验证，纠正一个常见误判）

README 表格的 **523 条 = 运行时以 `  ok` 开头的输出行数**，逐文件实测完全吻合：

| 套件 | 运行时 `ok` 行数 | 静态 `ok(` 调用点 |
|---|---:|---:|
| ballistics | 39 | 35 |
| mapgen | 97 | 46 |
| mapgen_mc | 45 | 40 |
| rules | 89 | 88 |
| vision | 76 | 76 |
| units | 53 | 53 |
| bot | 8 | 8 |
| match_test | 116 | 107 |
| **合计** | **523** | **453** |

差额来自循环展开（如 `mapgen_test.js:195` 在 12 seed × 4 VP 内重复执行）。所以**数字可复现、不是编造**；但项目没有测试框架、不输出断言总数，`test/all.js:45` 只报套件数，523 只能靠 `grep -c` 手工统计。10 个套件中有 2 个根本不用 `ok()`：`web_smoke.js` 是单个复合布尔，`tournament.js` 只检查 `determinism.ok`，无独立断言。

### 3.2 独立变异实验（本次实做，非引用历史数据）

在临时副本上做变异，原文件未改动：

| 变异 | 结果 | 说明 |
|---|---|---|
| M1 `BASE_INCOME 1.5 → 2.5` | **被杀死**（exit 1） | `rules_test.js §9` 的绝对字面量锚点有效 |
| M2 `VP_RADIUS 4.2 → 6.0` | **被杀死**（exit 1） | 3.5 格计分 / 5 格不计分的绝对锚点有效 |
| M3 `match.js` 中 VP 圆绘制半径 ×3 | **存活**（exit 0） | `web_smoke.js` 仍全绿，**渲染正确性完全未被验证** |
| M4 八领域权重数组 | `[0.25,0.15,0.15,0.15,0.10,0.05,0.05,0.10]` | 佐证 `match_test.js:64`「权重和为 1」是恒真断言 |

结论：**规则层的测试是有牙齿的**（v0.10 补的绝对基准确实修好了历史上的"变异体全存活"），但**渲染层是明确的覆盖黑洞**。

### 3.3 确凿的有效性缺陷（带证据）

1. **恒真 / 空洞断言**：`match_test.js:62`（`avgMs >= 0`）、`:64`（权重和 = 1）、`:472`（`R.N*64 > 200000`，纯算术且不触碰被测行为）、`units_test.js:212`（`length >= 0` 合取）。这些被计入 116/53 条断言。
2. **自指断言残留**：v0.10 只**新增**了 §9 的 20 条绝对基准，未删除旧的自指断言——`rules_test.js:248/250/262/269`（用 `R.BASE_INCOME`、`R.REPAIR_RATE`、`R.TYPES` 构造期望）、`ballistics_test.js:32-35`（同一 `B.fly` 用两种步长互比，积分器写错但步长无关时两边一起错）、`vision_test.js:259/281`。
3. **纯绊线被当强度**：`vision_test.js:100-113` 两条冻结哈希，代码注释自己承认「不证明行为正确」；历史 v0.9 审查实测 14 个变异体中 **7 个仅被绊线杀死**。且 README:320 记录的哈希 `84ca0591…/1b857d06` 与代码中的 `e617cb5d…/906f1b14` 不符，文档已失效。
4. **异常被吞**：`rules_test.js:36-43` 的 `send()` 把 `decode` 异常 catch 成 `{error}`，约 30 处调用**全都不检查返回值**。
5. **入口判定过松**：`test/all.js:35` 只信 `r.status === 0`，不检查 stderr、`FAIL` 字样、断言哨兵或断言数；崩溃/超时靠 `null !== 0` 碰巧判失败。
6. **覆盖率统计有结构性漏洞**：`coverage.js:112` 只遍历**实际采到**的文件，THRESHOLDS 里 8 个文件任一漏采即静默跳过门槛；`:73-74` 分母随意剔除注释/字符串行；只有行覆盖，无分支/函数覆盖；`:11-13` 明确把 `match.js` 排除在统计外。所谓「99%」是单文件 `rules.js` 的数字，不是全项目。
7. **时间墙钟断言会 flaky**：`mapgen_test.js:365`、`mapgen_mc_test.js:251` 用 `ms < 25000` 做性能判定，在插桩或高负载 CI 上会误报（本次插桩实测放大 12.8× 已印证）。
8. **测试与实现强耦合**：直接改内部状态（`rules_test.js:111/122/185`、`match_test.js:273/291/332`）、专用 `INTERNALS` 后门、写死 `protoVersion===5` / `tickMs===50`。这些是白盒测试，**无法随迁移到 Go 版带走**。

### 3.4 确实做得好的地方（应予保留）

- `rules_test.js §9` 的绝对数值锚点（14.4 / 5.52 / 1.5 / 24 / 22 / 4.2 格 / 7.5 m / 30 m），是本次变异实验能杀错的原因。
- **假时钟注入**（`match_test.js:145-151, 377-390`）消除忙等；**固定坐标构造地形**（`vision_test.js:36-62`、`units_test.js:35-57`）不再碰运气找山脊。
- 大量**负例 / 篡改对照组**：封山→断开→`carveCorridor` 恢复、篡改 orderLog/首帧哈希/winner 必须被 `verifyDeterminism` 抓到、开雾/关雾对照、「只差一个节点仍会研究」防假绿。
- **独立 oracle**：`mapgen_test.js` 自写连通块与结构张量、12 seed 逐格 180° 对称、双方到 VP 距离多集相等。
- `verifyDeterminism()` 是真实现（重建 Game + 逐拍重放 + 帧哈希比对），「视野只改信息集不改模拟」用逐帧哈希钉住。
- 冻结防作弊有端到端验证，并**诚实标注「冻结不是安全边界」**。

## 5. 架构分析

### 5.1 模块划分与依赖

11 个 `referee/*.js`（约 6,000 行）+ `scripts/` + `test/`。依赖方向单向：`ballistics / mapgen / mapgen_mc → rules → referee → tournament`，**无 require 环**；但存在两层隐性耦合：

- **逻辑回环**：`rules.js:468` 的 `GENERATORS` 映射调用 MC 生成器，而 `mapgen_mc.js:422` 反向回调 `mapgen.js` 的 `finalize`。靠 `MAP_OPTS` 参数下发避免双向 require，代价是生成器必须知道收尾流程的内部结构。
- **跨模块常数靠约定**：`ballistics.js:50-53` 注释自承 `CELL_PX=6` 拿不到 `rules.js` 的 `CELL`，只能靠 `rules_test.js:30` 一条测试守着相等。

**8 个模块是 UMD 双模式**（`module.exports` / `globalThis.WoDRef`），浏览器靠 `match.html:110-117` 的 `<script>` 顺序注入全局。这是为「同一份源码同时跑 Node 测试 + 浏览器 demo + vm 冒烟」服务的原型技巧，Go 版没有对应需求。

### 5.2 `rules.js` 是可维护性的主要瓶颈

1,738 行单文件，`Game` 类 **56 个方法、6 类职责混杂**：

- 模拟：`step()` 142 行 God function，一个函数内完成指令归一化、阵营动作、经济生产、单位意图、开火弹道、炮弹推进、死亡清理、VP 判定、帧哈希共 9 个阶段。
- 协议：`header/encodeHello/encodeTick/encodeEnd/decode` **全部写在 Game 类里**（`decode()` 109 行同时做协议校验、语义丢弃与记账）。
- 计分：`computeCards()` 八领域公式硬编码在 `f[]` 数组里。
- 视野 / 信息集：散落在模块级 `losClear/canSee/visionGrid`、`encodeTick` 内联过滤、`step()` 内联判断三处。
- 确定性：`hashFrame`、`orderLog`、`frameHashes` 与模拟共用同一对象。

**协议层实际并未分离**：`referee.js:217` 的 `start(g.header())` 和 `:280` 的 `finish(rec.result)` 都是**对象直传**，`encodeHello`/`encodeEnd` 只在 `match_test.js:182/186` 被调用过一次验证标签，**从未进入真实链路**；只有 `tick` 走了 `JSON.parse/stringify` 字符串，且仍是同进程函数调用。

### 5.3 重复逻辑与魔法数字

- 坡度/通行判据写了 **3 份**：`rules.js:501`、`mapgen.js:701`、`bots/tactical.js:30/60`（注释自承「否则流场会推荐裁判走不过去的格」）——正是 Plan_Beta §1.3 要求共用同一份源码要消灭的漂移。
- 平台坡限 `55` 散落 4 处；沙丘剖面、河漫滩扩散各 2 份；`elev` 编码同时存在 `surfString` 与 RLE+base64 两套。
- 魔法数字集中在 `applyMove`（1207-1220）、`solveShot`（1272-1280）、`computeCards`（1441-1453）、`decode`（1101-1202）。
- **无 schema / 类型定义 / 机器可读接口文档**：无 `.d.ts`、无 JSON Schema、无 proto；协议靠 README 表格 + `header().rules` 运行时快照。新增一个单位至少要改 **10 处**（TYPES、RPS 行列、PRODUCIBLE、spawn 特例、carrier 特例、行为函数、渲染分支、配色表、文档表格、测试）。
- 唯一接近插件化的是地图生成器（两套 + 共用 `finalize`），这是架构里最值得保留的设计。

### 5.4 确定性与隔离（迁移的最大技术债）

- **帧哈希跨语言不可移植**：`fnv1a` 按 UTF-16 code unit + `Math.imul`，输入是 `JSON.stringify(...)`，键序依赖 JS 插入顺序；Go `encoding/json` 对 map 按字典序、struct 按字段声明序 → 必然对不上。`referee/README.md:257` 自己已警告「换 Go 需按语言重算哈希」。
- **浮点边界**：RK4 + `Math.hypot/pow/sin/cos`、`Float32Array` 量化 `Math.round`、命中/落地阈值比较，末位差异即可翻转命中结果；`rules.js:296-299` 注释承认视线判定曾因浮点末位不对称。
- **墙钟进计分**：`rules.js:1437/1452` 用真实 `decide` 耗时算第 8 领域（权重 10%），`verifyDeterminism` 只比 `winner/level`、不比 `cards.total`，所以「确定性通过」**不保证总分可复现**。
- **隔离不是安全边界**：Bot 是同进程对象引用（`referee.js:79` 直接 `bot.decide(state, mem)`），无子进程、无白名单、无 CPU 限制、无法中断死循环；`deepFreeze` 只防「改常量 / patch 原型」，防不住 `require('fs')`、读全局、耗尽 CPU。换边只是 `new Game` + 重新 `init`，闭包不清空（`referee/README.md:25` 自承不等价于进程重启）。

### 5.5 性能与规模

- 256² 下 `visionGrid` 是主要开销：`O(U · rad² · losSteps)`，每单位扫 `(2rad+1)²` 方框逐格 `losClear`；逐 tick 开火候选扫描 `O(U²)`、炮弹命中 `O(P·U·5)`。
- 放大到 512²：格子数 ×4，`SCALE` 4→8 使视距/采样半径翻倍，**视野开销约 ×8**；`elev` 逐格 base64 从 87 KB → ~350 KB；`MAP_CACHE` 与 32 次 attempt 内存同步放大；逐帧 `frameHashes` 随局长线性增长。
- `GRID`/`CELL`/`M_PER_CELL`/`CELL_PX` 构成隐式换算链，改 GRID 会连锁影响全部坐标与弹道——**不是配置开关**。

## 8. 可行性结论（明确判定）

### ✅ 可行：把 MVP 当作**可执行规约与差分预言机**

- 冻结后的 JS 版本可作为规则语义的唯一权威解释：五级判定链、八领域计分口径、四项分配、科技树、弹道与地形算法、`step()` 的 9 阶段顺序、地图对称与连通收尾流程，都可直接翻译为 Go 的公式与判定顺序。
- 可作为 golden trace 生成器、平衡调参沙盒、Go 版对拍的 oracle。
- 零第三方依赖约定、确定性重放方法、独立 oracle 测试写法、诚实的风险登记文化，都值得继承。

### ❌ 不可行：把 MVP 的**代码架构**直接用于主项目

以下 5 个原型包袱会随代码一起带进正式版，且每一个都与 Plan_Beta 冲突：UMD 双模式 + 全局命名空间、同进程 Bot 调用、`JSON.stringify`/FNV-on-UTF-16 的哈希体系、256² 的地图编码与视野实现、墙钟进计分卡。叠加 `rules.js` 单类 56 方法、协议与引擎焊死、无 schema，直接沿用等于把重构债提前固化。

### 判定：**有条件可行（Conditional Go）**

> 以 MVP 冻结版为**规格与对拍基准**，主项目按 `protocol / engine / scoring / io` 四层用 Go 标准库重写，选手只交 `decide.go`、编译为独立进程；**不搬 JS 代码结构，不在 JS 上继续加功能**。

**前置门槛**：第 7 节 P0 五项全部完成，且 `npm run ci` 全绿、golden trace 可产出。在此之前启动 Go 重写，会失去唯一的验证锚点——因为当前快照既未提交、CI 又红、需求基线还悬着，一旦重写开始就无法判断"Go 版和谁对齐"。

**补充判断**：由于主项目目前零代码、空骨架、需求文档未入库，这其实是**重新立基线成本最低的时点**。建议把「先花小代价把 MVP 固化成可复现 oracle，再开 Go」作为唯一推荐路径；跳过固化直接重写，或用 MVP 顶替正式引擎继续办赛，都应明确否决。
