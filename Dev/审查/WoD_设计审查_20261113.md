## 0. 结论

**一句话**：`Dev/MVP` 是一套**测试扎实、可复现的规则引擎**，但还不是一场**能评估 AI 能力的比赛**：官方“正式比赛测试”只有 2 局、1 个 seed；我补跑 100 局后，结论与官方测试相反（Tactical 85 胜 13 负 2 平），说明当前决定结论的是评测协议，而不是策略强弱。

| 维度 | 判断 | 主要依据 |
|---|---|---|
| 引擎完整度 / 测试 | **强** | 10/10 套件通过（165 s）、覆盖率阈值、116 条裁判断言、89 条规则断言、视野/模式/弹道/地图全实现 |
| 可复现 / 审计 | **强** | 逐 tick `frameHashes`、`orderLog` 重放、换边、连续 3 次红牌、逐局归档 |
| 玩法 / 考察面 | **中弱** | 100 局：98 局 L2、2 局平、**0 局斩舰**；21 局有开火、11 局有击杀；4/7 可生产兵种；7/20 科技；全部 `obey` |
| 评测 / 统计 | **弱** | 官方测试 2 局/1 seed；无 BT/CI/并列；八领域约 45 分常数；VP 与总分相关 0.808 |
| 交付 / 竞赛 | **中弱** | 自包含包 + manifest + 10 套件（强）；无正式许可、无英文版、无模型条件、无沙箱、无赛季 |
| 规范符合 | **部分** | 目录/README/CONDITIONS/prompt/bots/replays/challenge 多处不符合正式集数结构 |

**五条关键判断**

1. **官方 2 局是异常样本。** 官方测试（seed 20261109）Tactical 0 胜 2 负、954:965、0 击杀；我用同一对 Bot 跑 50 个 seed / 100 局，Tactical **85 胜 13 负 2 平**，而 seed 20261109 的两局**都是 Greedy 胜**。用 2 局判断“Tactical 不如 Greedy”是抽样错误。
2. **计分卡仍然退化。** 100 局均值：母舰完整度 100、算力 99.88、KD 50、保存兵力 99.10、推进效率 95.00；前四项按权重约 **44.9 分是常数**，推进再贡献约 4.75 分准常数。VP 与总分相关 0.808。
3. **胜负仍由 VP 决定，斩舰没有发生。** 100 局里 98 局是 L2（时间到比 VP），2 局 L5 平局，**0 局 L1（母舰被毁）**；只有 21/100 局出现开火、11/100 局出现击杀，合计 28 次击杀。一个不做寻路的 LAV 冲锋探针在 6 局里 0 斩舰、0～3 击杀。
4. **机制“有实现，没被用上”。** 20 seed / 40 局逐帧统计：可生产兵种只出现 LAV/AAV/SALVAGER/CARRIER（SCOUT/RAILGUN/ARTILLERY 为 0）；科技树 20 节点只出现 7 个；行动模式 89,805 个单位帧**全部是 `obey`**；Tactical 的 13 节点研究路线在 600 tick 内只走到 7 个。
5. **交付层比 Go 半成品好，但仍不是竞赛包。** `正式比赛测试/workspace` 是自包含的（engine 快照、arena.js、bots、manifest、10 套件），这点强于 `war_of_desert`；但没有正式许可、`README_en`、模型条件、Docker 沙箱、赛季/BT、归档 HTML 回放。`hello` 约 110 KB，契约仍是 64 KB，测试却按 128 KB 断言。

**建议**：保留这套引擎和测试；先补“竞赛层”（固定 seed 池、50+ seed、80～120 局/人、基准锚 + 并列 + CI、模型条件、许可），再谈“AI 能力榜”。如果现在投稿，定位应为“社区竞赛规则引擎 + 本地测试环境”，不是“正式赛季”。

## 1. 更正与三层结构

这次误判不是孤立的：仓库里对“正式版”有三套互相矛盾的说法。

| 层 | 位置 | 仓库里的说法 | 实际角色 |
|---|---|---|---|
| 设计意图 | `Dev/Plan_Beta.md` | “v1.0 规则基线，已生效” | 目标契约：256²、20 TPS、600 tick、120 ms、3 次红牌、视野可配、BT + 八领域 |
| 参考实现 | `Dev/MVP` | “MVP v0.10 · 规则原型”；`Dev/README` 说“`MVP/` 是规则源码，不参与正式赛执行” | 完整 JS 引擎 + 10 套测试 + 2 个 Bot + 正式比赛测试环境；**用户指定的正式版** |
| 执行链尝试 | `war_of_desert` | 根 README“正式版 v1.0 已落地”；`Dev/README`“正式比赛在隔壁目录” | 围绕 `MVP@288db07` 快照的 Go 执行链；Go 引擎未实现，**用户指定的半成品** |

三种“正式”并存，直接导致：

- 读者不知道哪份代码是事实源（我第一版就按根 README 审了 `war_of_desert`）；
- `war_of_desert` 的 40 局基准赛被当成“正式赛季成绩”，而它其实是半成品的自测；
- `Dev/MVP` 明明是唯一完整实现，却自称“原型”，在 README 里被排除在正式赛之外。

> 另外，攻守实验（`rules_siege.js`、母舰 HP 1250/工事 16/1260 tick）只存在于 Go 半成品，`Dev/MVP` 没有实现它；它不是正式版的一部分，本文只在附录 C 提及，不纳入游戏设计评估。

**与上一版相比，有三处结论反转**：

1. **选手包**：上一版说“不能独立编译”，那是 Go 半成品；正式版的 `正式比赛测试/workspace` 是自包含的，移动目录仍能跑。
2. **引擎测试**：上一版只看到 Go 执行链；正式版有 10 个套件、覆盖率阈值、116 条裁判断言，工程质量明显更高。
3. **名次**：上一版说“BT 区间太宽”；正式版**根本没有 BT**，只有积分榜。问题不是区间宽，而是没有统计模型。

**这是投稿前必须先修的结构问题**：指定一个事实源（建议 `Dev/MVP` + `Plan_Beta`），其余两份明确标注“移植中/历史”，根 README 首屏写清三者关系。

## 2. 正式版是什么

### 2.1 组成

```text
Dev/MVP/
├── README.md                 40 KB：规则、数值、设计取舍、已知问题
├── referee/
│   ├── rules.js              101 KB：模拟 + 协议 + 计分 + 地图 + 确定性（1769 行，Game 56 个方法）
│   ├── referee.js            20 KB：hello/tick/end、50 ms tick、120 ms 预算、3 次红牌、逐局归档
│   ├── tournament.js         8 KB：多 Bot × 多 seed × 换边、积分榜、确定性复核
│   ├── match.js / match.html 网页观战（实时跑两局，可导出 replay.json）
│   └── bots/{greedy,tactical}.js  80 / 289 行，两个独立策略
├── test/                     10 个套件：弹道、两套地图、规则、视野、单位模式、Bot 分支、裁判、网页、循环赛
├── scripts/coverage.js       零依赖 V8 行覆盖 + 阈值门槛
└── 正式比赛测试/
    ├── workspace/            自包含选手包：RULES、arena.js、engine 快照、bots、submission、replays、results
    ├── workspace_manifest.json  逐文件 SHA-256
    ├── 开赛.py               90/120 分钟计时、暂停、强制收卷
    └── 全流程测试报告.md      2 局正式测试 + 4 局批量回归
```

### 2.2 它做对了什么

- **引擎完整**：地形、坡度、山脉阻挡、RK4 外弹道、弹种/装甲、经济、生产、科技、母舰四项分配、武器独立队列、运载舰、SCOUT、三种行动模式、视野（山脉遮挡 + 战争迷雾 + 高差加成）都实现并有测试。
- **测试扎实**：10 个套件全部通过；`test/all.js` 汇总 165 s；`rules_test.js` 89 条、`match_test.js` 116 条、`mapgen_test.js` 97 条、`vision_test.js` 76 条、`units_test.js` 53 条断言；覆盖率有阈值，低于阈值 CI 失败。
- **可复现**：每局 `frameHashes` 逐 tick 比对，`orderLog` 重放；换边；确定性校验有失败分支测试；`match_test` 还用 1 ms vs 90 ms 的决策耗时验证“耗时进不了状态”。
- **选手包自包含**：`正式比赛测试/workspace/engine/` 是 `MVP@288db07` 的裁判快照，`arena.js` 不读 `../../referee/`；移动整个目录仍能运行；`workspace_manifest.json` 逐文件记 SHA-256。
- **两个独立 Bot**：`greedy` 是“不研究、只堆 LAV”的基线；`tactical` 会分阶段分配、走工业/火力/机动路线、用 BFS 流场认领 VP、造运载舰前压。它们不是同一骨架的参数变体。

### 2.3 它不是什么

- **不是一场比赛**：没有参赛模型、没有模型条件、没有赛季、没有 BT/名次、没有固定地图池；`正式比赛测试` 明确写“不要求模型现场编写策略”，只是流程验证。
- **不是正式赛执行链**：`Dev/README` 说“正式赛跑的是 `war_of_desert/` 的 Go 执行链”；但那条链的 Go 引擎尚未实现，所以“正式版”目前只在 JS 层成立。
- **不是隔离环境**：`MVP` README 自己写“冻结不是安全边界；Bot 与裁判仍然同进程；require/全局/CPU 都拦不住”。

## 3. 游戏设计评估

### 3.1 宣称的复杂度

规则宣称四个维度：

1. **地形**同时影响移动、射程、伤害、视线与寻路；
2. **母舰**不是兵，是资源分配器（生产/攻击/研究/移动四项百分比）；
3. **经济/科技**：单 CU、采集车、四条科技树（2 线性 + 2 交叉，共 20 节点）；
4. **弹道**：二次阻力 + 重力、RK4、落速/弹种/装甲/克制决定伤害；
5. **信息**：视野可开（山脉遮挡 + 战争迷雾 + 高差加成）；
6. **单位自治**：`obey / neutral / aggressive` 三种模式。

### 3.2 100 局实测（正式版，Tactical vs Greedy，50 seeds × 换边）

| 指标 | 结果 |
|---|---|
| 局数 | 100（50 seeds × 2 局） |
| 胜负 | **Tactical 85 / Greedy 13 / 平 2** |
| 判定层级 | L2 98、L5 2、**L1 0** |
| 开火 | 714 发；**21/100 局**有开火 |
| 击杀 | 28 次；**11/100 局**有击杀；单局最多 8 |
| 分差 | VP 差 p10/中位/p90 = 20 / 378 / 666（满分 2400） |
| 平均总分 | 61.17（Tactical 62.97 / Greedy 59.37，sd 4.70） |

**分 Bot：**

| Bot | 胜 | 开火 | 命中 | 击杀 | 阵亡 |
|---|---:|---:|---:|---:|---:|
| Tactical Flow | 85 | 24 | 23 | 13 | 15 |
| Greedy Rush | 13 | 690 | 370 | 15 | 13 |

Greedy 打了 690 发、命中 370 发，却只赢 13 局；Tactical 只打 24 发，靠 VP 与科技赢 85 局。**这不是“谁打得准”，是“谁占得住点”**。

**八领域（100 局，200 个参赛方）：**

| 域 | 权重 | 均值 | 标准差 | 对总分贡献 | 判断 |
|---|---:|---:|---:|---:|---|
| VP 控制 | 25% | 30.11 | 11.28 | 7.53 | 唯一大信号 |
| 歼敌 | 15% | 0.90 | 5.33 | 0.14 | 近乎恒 0 |
| 保存兵力 | 15% | 99.10 | 5.33 | 14.87 | 近常数 |
| 母舰完整度 | 15% | 100.00 | 0.00 | 15.00 | **恒 100** |
| KD 差 | 10% | 50.00 | 8.72 | 5.00 | 178/200 个参赛方恒 50（约 89%） |
| 战场控制 | 5% | 78.12 | 24.93 | 3.91 | 与 VP 高度相关 |
| 推进效率 | 5% | 95.00 | 21.79 | 4.75 | 与 VP 重复、饱和 |
| 算力表现 | 10% | 99.88 | 0.03 | 9.99 | **恒 99.9，机器相关** |

- **约 44.9 分是常数**（保存 14.87 + 母舰 15 + KD 5 + 算力 9.99），推进再贡献 4.75 分准常数；真正变化的只有 VP（7.5）、控制（3.9）、歼敌（0.14）。
- **VP 与总分相关 0.808**；把“八领域加权”叫品质信号，实际是“VP + 控制 + 一个大常数”。
- **推进效率与 VP 共用计数器**：`rules.js` 里 `vpScore++` 与 `vpTicks++` 同时发生；分母 `denom/6` 让它在占住 1/6 时间时就饱和到 100。均值 95 就是证据。
- **保存兵力反向激励**：`aliveCost / producedCost` 在“不生产、不损失”时是 100；少造兵反而更容易拿满 15 分。
- **算力域测的是 IPC**：`1 - avgBot/120` 在 0.05～0.07 ms 时是 99.9；没有按 `Plan_Beta` §5.3 做机器校准。

### 3.3 机制覆盖（20 seeds / 40 局逐帧）

| 机制 | 可用 | 40 局实际 | 判断 |
|---|---|---|---|
| 兵种 | 7 可生产 + 母舰 | LAV、AAV、SALVAGER、CARRIER、MOTHERSHIP；**SCOUT/RAILGUN/ARTILLERY 为 0** | 4/7 可生产兵种 |
| 科技 | 4 树 20 节点 | 出现 7 个：I1/M1/F1/I2a/M2a/F2/I3a | 单局平均 3.3 个 |
| 行动模式 | obey/neutral/aggressive | 89,805 个单位帧**全部 `obey`** | 2/3 未测 |
| 母舰武器 | 5 槽独立队列 | 少量 1 门；未到 5 槽 | 名义机制 |
| 视野 | 可开雾 | 默认关闭，两个 Bot 都不消费情报 | 开/关胜负一样（README 自认） |
| 场景事件 | 无 | 无 | 无重规划压力 |

### 3.4 解读：为什么是“占点 + 科技”而不是“合成兵种”

1. **4 个 VP 对 2 个玩家太多**：双方可以各拿各的点；`tactical` 的 BFS 认领 + 驻守就是最优解，`greedy` 的“全军压一个点”反而挤在一起。
2. **30 秒装不下科技树**：`tactical` 的 13 节点路线在 600 tick 内只走到 7 个；RAILGUN（320 CU / 60 tick）订单没有落地，CARRIER 只少量出现。科技树是“路线选择”，不是“全树展开”。
3. **母舰 3000 HP + 自动开火 + 伤害摊薄**：`greedy` 8～10 辆 LAV 的伤害被分散到多个目标；100 局 0 斩舰。MVP README 的“已知问题”也承认“击杀摊薄、KD 长期 50”。
4. **没有信息差、没有事件**：视野默认关；两个 Bot 都不看敌方情报；没有沙暴/补给/VP 易手/突然死亡。最优策略是静态的“认领—驻守—攀科技”。
5. **斩舰探针失败**：我写了一个不做寻路、全军直冲敌方母舰的 LAV 冲锋 Bot，对 Greedy/Tactical 各跑 3 个 seed，**6 局全负、0 斩舰、0～3 击杀；对手 0～13 击杀**。这说明“直冲母舰”不是可行策略；更强的最优突袭是否可行未被验证，但**当前没有任何 Bot 覆盖 L1**。

**结论**：正式版的游戏是“**VP 占点 + 经济/科技路线**”的游戏，不是“地形/弹道/合成兵种”的游戏。Tactical 85:13 证明策略有高低，但高低主要来自“分配/科技/认领”，不是“交战/克制/协同”。

### 3.5 作为 AI 能力考题，考到了什么

| 能力 | 是否考到 | 证据 |
|---|---|---|
| 协议/接口理解 | 是 | 2 个 Bot 都实现 init/decide；10 套件覆盖协议 |
| 地图解码 + 寻路 | 是 | tactical 自建 BFS 流场；山脉/坡度约束 |
| 经济/生产/科技状态机 | 是 | 分阶段分配、13 节点路线、运载舰补兵 |
| 长期规划 | 部分 | 600 tick 内只能走 7 个节点；路线选择有意义 |
| 战术/交战 | 弱 | 21% 局有开火、11% 局有击杀；Tactical 只打 24 发 |
| 信息不对称下的决策 | 否 | 视野默认关；Bot 不消费情报 |
| 对手建模/欺骗 | 否 | 两个 Bot 都不预测对手；无假动作/佯攻 |
| 计划被打断后的重规划 | 否 | 无场景事件；VP 只累计不衰减 |
| 多兵种协同 | 否 | 4/7 兵种出场；无集火/阵型/掩护 |

## 4. 评测设计

### 4.1 官方 2 局是异常样本（最重要的问题）

官方 `全流程测试报告.md`：


我复现同一 seed，结果一致。但把同一对 Bot 扩到 50 seeds / 100 局：

```text
Tactical 85 胜 / Greedy 13 胜 / 2 平
seed 20261109 的两局都是 Greedy 胜
```

（`submission/bot.js` 是 greedy 逻辑的可运行副本；seed 20261109 下它与 `bots/greedy.js` 给出同一结果 954:965，所以我用 `greedy.js` 做 50 seed 探针。）

**结论**：官方测试没有统计力。它作为“流程验证”是合格的（README 也这么定位），但不能用来判断“Tactical 不如 Greedy”或任何平衡结论。当前仓库没有任何地方声明“2 局不做平衡结论”，读者很容易误读。

**同一 seed 的官方数据还互相矛盾**：

- `Dev/MVP/README.md` 的“实测（seed 20261109 / 600 tick × 2 局）”写 Tactical 2:0、VP 1019:990、总分 67.0:61.6；
- `Dev/MVP/正式比赛测试/全流程测试报告.md` 写 Tactical 0:2、VP 954:965、总分 62.81:65.05；
- README 的文字还写“Tactical 仍然 5:1 领先胜场”，但表里只有 2 局；总分 393.2:376.6 也对不上 2 局表。

两份都称 seed 20261109、600 tick、换边两局，结果却相反。我用当前 `bots/tactical.js` vs `bots/greedy.js` 复现同一 seed，得到 954:965（Tactical 负），与正式测试报告一致、与 README 表不一致——README 的“实测”与当前代码不符（旧数据或未更新）。这是“可评估性”的直接问题：读者无法判断哪份数据是事实。

### 4.2 没有 BT、没有区间、没有并列

- `tournament.js` 是**积分榜**：胜 1、平 0.5、负 0；按积分、再按八领域总分排序。
- 没有 Bradley–Terry，没有 95% 区间，没有“相邻差 CI 含 0 记并列”。
- 只有 2 个 Bot，积分榜只能回答“这 2 个谁赢得多”；14 个模型参赛时会退化成“谁抽到的对手弱”。
- 正式集数的口径是“基准 = 0、相邻 CI 含 0 记并列、千-万局、按地图整块 bootstrap”；`tank` 是 14400 局、60 张新图、基准锚；`rmuc2026` 至少明确“同分并列”。WoD 正式版这三项都没有。

### 4.3 计分卡：约一半是常数

见 §3.2。补充两个量化后果：

- **算力域 10% 权重**：均值 99.88、sd 0.03；在 100 局里它几乎不区分 Bot，却占总分 10 分。
- **冠亚军差距在 2 局样本里没有意义**：官方 2 局 Tactical 125.63 vs Greedy 130.10（差 4.47）；100 局均值 Tactical 62.97 vs Greedy 59.37（差 3.60）。2 局样本本身不足以支撑“谁总分高”；算力域只是给双方各加约 10 分，不提供区分度。

### 4.4 seed / 地图协议

- `arena.js` 默认 seed `20261109`；`正式比赛测试` 正式单局也用它；**练习 seed = 官方 seed**。
- 官方测试只跑 1 个 seed；`batch` 默认只跑 4 局；没有固定地图池。
- `tournament.js` 的设计比 Go 半成品好：`seeds.forEach(seed => 每个 pair 都打)`，所有选手共享同一组 seed；但缺少“地图池固定 + 赛前抽签/冻结”的正式协议。
- 选手拿到仓库即可提前算出所有 seed 的地图；规则只禁止硬编码单图坐标，没有禁止“按 seed 分支”。

### 4.5 冻结链

- `开赛.py` 把 `workspace/submission/bot.js` 复制到 `交卷/bot.js`，记录 SHA-256、用时、`accepted`。
- `arena.js` 读的是 `workspace/submission/bot.js`，**不读 `交卷/`**；冻结副本不参与评测。
- `workspace_manifest.json` 覆盖 workspace 文件，但 `arena.js` 启动时不做清单校验；收卷哈希也不与清单比对。
- 结论：冻结是“留档”，不是“防替换”。

### 4.6 `hello` 体积

- 实测 256² `hello` 约 110 KB；`referee.js` `MAX_LINE = 65536`；`match_test.js` 断言 `hello < 128 KB`。
- 契约（64 KB）与测试（128 KB）不一致；外部 Bot 若按 64 KB 写 reader 会截断。
- `MVP README` 自己把 512² 的 `hello` 估算为 440 KB，说明这是已知的编码瓶颈，不是小问题。
- **正式地图尺寸口径不一**：`Plan_Beta` §2 写 256²、§8 写“512² 延后”；`MVP/README` 的“与计划的差异”却写“正式版 512²”。读者无法判断正式版到底是 256² 还是 512²。

## 7. 对三个问题的直接回答

### 7.1 作为“AI 算法能力与复杂场景应对”的考验，是否合理充分？

**结论：引擎层面合理，竞赛层面不充分。**

合理的部分：

- 规则不是玩具：地形影响移动/射程/视线，弹道是 RK4 外弹道，经济/科技/分配有真实取舍，600 tick 内有路线选择。
- Tactical vs Greedy 的 85:13 证明“会管理分配/科技/认领”确实能赢“只会堆兵”，策略有高低。
- 10 套件 + 覆盖率说明规则实现的可信度高，不是“看起来复杂、实际跑不通”。

不充分的部分：

1. **复杂场景没有发生**：0 斩舰、21% 局有开火、11% 局有击杀；没有雾（默认关）、没有事件、没有强制接触。所谓“复杂场景应对”没有被任何一局覆盖。
2. **获胜轴太窄**：Tactical 只打 24 发就赢 85 局，靠的是 VP 认领 + 科技/分配；Greedy 打 690 发只赢 13 局。这说明“打得多”不如“站得住”，但也说明“交战/克制/协同”不是胜负关键。
3. **机制大量闲置**：SCOUT/RAILGUN/ARTILLERY 为 0；三种模式只用 `obey`；20 节点科技只走 7 个；母舰 5 武器槽未用满。规则宣称的“合成兵种”没有进入对局。
4. **没有对手建模**：两个 Bot 都不看敌方情报；全图可见（默认）；确定性；无随机事件。最优策略是静态规划，不需要预测/欺骗/反制。
5. **样本量不足**：官方 2 局/1 seed；补充探针 100 局只有 2 个 Bot。它不能回答“哪个模型更强”，只能回答“这两个手写 Bot 谁赢得多”。

**要成为充分的考题，至少需要**：

- 强制接触：1 个中心 VP + 2 个侧翼 VP，或 VP 衰减/突然死亡；
- 信息不对称：开雾赛季，SCOUT 有真实收益；
- 动态事件：沙暴/补给/VP 易手，考重规划；
- 多样对手：3 种独立实现的参考 Bot + 弱基准 + 搜索型参照；
- 足够局数：每人 80～120 局、固定地图池、BT + 并列 + CI；
- 可解释评分：每个域有方差、与胜负不重复、机器无关。

### 7.2 设计是否清晰且可评估？

**结论：引擎清晰，竞赛不可评估。**

清晰的部分：

- 规则源码在选手包内，`RULES.md` 指向 `engine/rules.js`；伤害/弹种/科技/分配都能查。
- 协议 `init/decide` 简单；`arena.js` 本地可跑；10 套件覆盖主要分支。
- 逐 tick `frameHashes` + `orderLog` 让“同 seed 同结果”可验证。

不可评估的部分：

1. **官方样本 2 局/1 seed**：不足以支撑任何强弱/平衡结论；且 seed 20261109 是异常样本（100 局里 Tactical 85 胜），而 README 与正式测试报告对同一 seed 给出相反结果（README 2:0，正式 0:2）。
2. **没有 BT/CI/并列**：`tournament.js` 是积分榜，2 个 Bot 时可以排名，14 个模型时会退化。
3. **计分卡一半常数**：母舰 100、算力 99.9、KD 50、保存 99.1、推进 95；总分与 VP 相关 0.808。
4. **机制未覆盖**：0 斩舰、4/7 兵种、7/20 科技、1/3 模式；这些维度没有数据，不能评估。
5. **冻结链断裂**：收卷 `bot.js` 不参与评测；manifest 不校验；`hello` 超契约。
6. **没有模型条件**：没有模型/工具/渠道/用时/事故表，无法判断“成绩差异”是模型能力还是条件差异。
7. **规则文档太薄**：`RULES.md` 只有 1.9 KB，不含单位表、科技效果、伤害公式、克制表；精确语义要读 101 KB 的 `rules.js`。模型在 90 分钟里既要读协议又要读引擎，容易把 `range=12.8`（世界格）当像素用——Go 半成品的 `refbot` 就是这么错的，正式版的 JS Bot 靠“不自己算射程、交给引擎自动开火”绕开了这个坑。

**一句话**：这套引擎“能跑出分数”，但当前协议“评不出能力”。

### 7.3 与正式集数规范、社区竞赛规范的符合程度

**正式集数规范**：符合 1 项、部分 6 项、不符合 9 项（见 §5.2）。核心缺口是目录结构、README_en、CONDITIONS、prompt、bots 投稿、replays HTML、LICENSE、自包含。

**社区竞赛规范**：符合 3 项、部分 6 项、不符合 4 项（见 §5.3）。核心缺口是许可、沙箱、ranked 标记、一键挑战、归档回放、非官方首屏声明。

## 9. 投稿建议

### 如果现在就要投到 `community/contests/`

**建议的定位**：不是“正式赛季”，而是“**社区竞赛规则引擎 + 自包含本地测试环境**”。这一定位与 `Dev/MVP` 的实际状态一致，也能保留它最强的部分（引擎、测试、manifest、本地 runner）。

**最小可行清单**：

1. **首屏声明**：社区非官方、规则引擎/测试环境、非模型榜、尚无模型参赛；把根 README 里“正式赛在 war_of_desert”改成“正式版在 Dev/MVP，war_of_desert 是移植中”。
2. **加 LICENSE**：MIT 或 CC BY-NC，与上游兼容；补 `THIRD_PARTY_NOTICES`。
3. **补竞赛层**：固定 seed 池 + 80～120 局/人 + BT/并列/CI；把官方 2 局明确标为“流程 smoke，不作平衡结论”。
4. **修计分卡**：删/改推进效率，保存兵力改相对期望，算力移出排名；加方差门禁。
5. **修冻结链/hello**：`arena.js` 读 `交卷/`，校验 manifest；hello 与 `MAX_LINE` 一致。
6. **补交付**：`README_en`、`CONDITIONS`、`prompt`、`bots/`、`replays/` HTML 播放器、`challenge.js`。

**如果做不到 1～4，建议不要以“社区竞赛”名义投**；可以改为“规则引擎/测试环境提案”，明确“尚无模型参赛、尚无赛季、尚无排名”，让维护者按提案评审。

### 值得保留的部分

- 10 套件 + 覆盖率 + CI：这是 WoD 最值钱的工程资产，正式集数也没有同等级的规则单测。
- 逐 tick `frameHashes` + `orderLog` 复核：比“只看胜负”的复现强一个量级。
- 自包含 workspace + manifest：比 Go 半成品的“目录式选手包”完整。
- 两个独立策略 Bot（greedy/tactical）：比 Go 的“同一骨架参数变体”更能验证规则。
- 非官方/非商业声明：虽然不在首屏，但意识是对的。
