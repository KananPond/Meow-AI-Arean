## 0. 结论摘要

| 问题 | 结论 |
|---|---|
| 测试能跑通吗 | 能。**7 套件全绿，322 条断言，0 失败，7.7–9.8 s**，零依赖、`node --check` 通过 |

| 符合 WoD 需求吗 | 裁判/协议/计分卡/确定性命中；**512²、进程隔离、Go、BT/Elo、选手包、回放播放器全缺**；`G3 地形影响移动` 至今无测试 |

一句话：**这是一份质量高于一般原型的「规则与协议验证件」，但不是能长大的「评测系统内核」；它的真正资产是协议形状、计分口径、确定性方法与平衡表，不是这 5000 行 JS。**

| `rules.js:316-326 pointVisible` | 飞行中炮弹的可见性过滤 | 「炮弹只按视距判」是 README 里的设计承诺，**没有任何断言** |

| `rules.js:1600-1604` | `step()` 对造炮槽位的二次校验（防绕过 decode） | 防线本身未验证 |

### 2.3 覆盖率表达不了的东西

- **进程边界**：Bot 与裁判同进程、同模块实例。测试只证明「`state` 是深拷贝」，**不证明「Bot 碰不到引擎」**（实证见 §3.5）。
- **跨语言一致性**：确定性测试是「同一个 JS 实现跑两遍」，无法证明 Go 版与 JS 版同解。
- **512² / 多人**：`Game(4)` 显式抛错，多人结算无代码也无测试；CELL/GRID 是模块常量，无法在不改源码的情况下换尺度。
- **并发/资源**：没有「同时跑 N 局」的压测，没有内存/CPU 上限验证。

## 3. 有效性：通过 ≠ 有效

### 3.1 变异测试：21.4%（去掉指纹绊线后）

14 个单点语义变异，跑完整套件：

| # | 变异 | 含绊线判定 | 纯行为判定 | 说明 |
|---|---|---|---|---|
| M1 | VP 半径 4.2→2.0 格 | 杀死 | **存活** | 用例把单位放在 VP 圆心，任何半径都成立 |
| M2 | 克制 LAV→Railgun 1.8→1.0 | 杀死 | **存活** | 断言写成 `TYPES.LAV.dmg * RPS.LAV.RAILGUN * …`，**用被测常量算期望值** |
| M3 | 基础收入 1.5→3.0 | 杀死 | **存活** | `gain > R.BASE_INCOME + …`，自我指涉 |
| M4 | 人口上限 24→40 | 杀死 | **存活** | 用例写 `g2.pop = R.POP_MAX`，跟着常量走 |
| M5 | 造炮价 120→20 | 杀死 | 杀死 | `vision_test` §8「钱不够时炮停在队列里等钱」是真断言 |
| M6 | 修理 2→0 HP/tick | 杀死 | **存活** | `abs(hp-(before+5*R.REPAIR_RATE))<1.5`，rate=0 时两边都是 0 |
| M7 | 坡度阈值 26/10→1000 | 杀死 | **存活** | **`MVP_plan` G3「地形影响移动」在裁判侧零验证** |
| M8 | 坡度减速因子→1 | 杀死 | **存活** | 同上 |
| M9 | 友军溅射 0.5→1.0 | 杀死 | **存活** | 没有友军溅射用例 |
| M10 | 命中半径 7.5→40 m | 杀死 | **存活** | 直击用例都正中，容不下「打偏」 |
| M11 | 阵亡不回收人口 | 杀死 | **存活** | 修这个 bug 的契约测试随人类版一起被删了 |
| M12 | 开火不再检查射程 | 杀死 | **存活** | 见 §3.2，用例取的 8 格弹道本身就够不到 |
| M13 | 分配过渡 5→50 点/tick | 杀死 | 杀死 | `t≥16` 的延迟断言是硬的 |
| M14 | 槽位封顶 3→1 | 杀死 | 杀死 | 槽位表是逐档断言的 |

**结论**：测试强在「物理与几何」（弹道、仰角、遮挡、积分收敛、扣费负数回归），弱在「规则数值与经济」（VP 半径、克制表、收入、人口、修理、溅射、坡度）——这部分普遍**用被测常量自证，等于没测**。

> **关于取样偏差，需要说明**：本轮的 14 个变异体**刻意集中在「规则数值 / 经济 / 坡度 / VP」这一片**，不是均匀采样。项目自己记录的「v0.8 视野 8/8 全杀」「v0.9 13 个变异 12 杀」很可能真实——但那批变异体集中在视野与行动模式，而那两块恰恰是 `vision_test`（72 条）与 `units_test`（53 条）密度最高的地方。两件事并不矛盾：**这个测试套件在视野/模式上是厚的，在经济/计分/地形移动上是薄的**。

### 3.2 一条被物理掩盖的射程断言

`units_test` §6 断言「8 格外不开火」。实测（压平地形、隔离单位）：

| 距离 | 2 格 | 3 格 | 3.4 格 | 4 格 | 5 格 | 8 格 |
|---|---|---|---|---|---|---|
| LAV 是否开火 | 是 | 是 | 否 | 否 | 否 | 否 |

LAV 设计射程 3.2 格（128 m），**弹道极限 5.5 格（218 m）**。射程门只在 **3.4–5.5 格** 这条带里可观测，而用例取了 8 格——那里是弹道自己打不到。所以删掉 `fire()` 里的射程判断，测试依然全绿。

**修法**：补一条 4 格的用例（期望 0 发）。这是 5 行代码、能立刻杀死 M12 的用例。

### 3.3 规则指纹绊线会被误读成测试强度

`vision_test` §2 把「122 tick × 2 方的协议行 SHA1」和 `rulesHash` 冻成常量。任何常数改动都会让它失败——这保证了「没人悄悄改规则」，**但它不验证行为**。本轮 14 个变异体里，有 7 个是「仅被绊线杀死」，行为断言全绿。

而且这条绊线在 v0.9 **是同提交重记的**（源码注释也承认：「v0.9 重记……这是有意的规则变更，所以重设绊线」）。它现在的语义是「别再悄悄改」，而不是「与旧版等价」。写进 README 时不宜表述为「逐字节一致」。

### 3.4 其它有效性弱点

- **白盒耦合**：测试直接改 `g.sides[0].cu`、`u.hp`、`g.map.elev`、`sides[0].techDone`，直接调 `g.fire / spawnShot / pickShell / solveShot / computeCards`。这 322 条断言里大部分**无法随迁移带走**，只能重写。
- **依赖特定种子的地图特征**：`vision_test` §3 用 `findRidge()` 在 seed 20261109 的图上找一条 1 格厚山脊。地图生成一改，测试就因「找不到山脊」而失败——**误报**，与回归无关。
- **时间敏感**：`decideMs:20` 配 30 ms 忙等、60 ms 忙等验 `late`。机器负载一高就 flaky。
- **自定义 harness**：`ok()` 只累加失败数，中途抛异常会静默跳过后续断言（退出码仍非 0，所以不会误判通过，但看不到「跳过了多少」）。无测试运行器、无 `describe/it`、无单测过滤。

### 3.5 隔离缺口（实测，不是推测）

**实验 A**：Bot 在 `decide` 里 patch `R.Game.prototype.encodeTick`，把双方全部单位塞回自己的 `state`（`vision: true` 下）：

```
作弊 Bot 看到敌方单位的决策次数 = 39 / 40
作弊 Bot 读到对手 CU = 38.5
故障数 = 0 ｜判定 = 时间到 · 全部相同，平局
```

**实验 B**：Bot 在 `decide` 里直接改共享规则表 `R.TYPES.LAV.dmg = 999`：

```
规则表 LAV.dmg: 8 → 999 ｜故障数: 0
```

`referee/match_test.js` §2 的「Bot 改不动裁判状态」只覆盖了**消息层深拷贝**，没有覆盖**同进程原型/模块级篡改**。规则表也没有 `Object.freeze`。对一个要收社区投稿、要给成绩定名次的比赛，这是**公信力级别**的缺口——正是 `Plan_Beta` §3.2 的进程隔离 + AST import 白名单要解决的问题。

### 3.6 值得肯定的部分

- 引擎内**没有 `Math.random` / `Date.now`**（只有 driver 计时用墙钟），随机全部走 `hash2/valueNoise(seed)`，这是确定性的真基础；
- `orderLog + frameHashes + verifyDeterminism` + 篡改检测，是「可复核成绩」的正确骨架，也是迁移时最该保留的方法论；
- 弹道部分断言用**绝对数值**（射程 <2% 误差、v² 律、落速 257→249），这类断言迁移后仍然有意义。

## 5. 架构评估

### 5.1 模块划分：实际是 6 个文件、5 个概念层，但职责边界不在文件边界上

| 文件 | 行数 | 承担的职责 |
|---|---:|---|
| `referee/ballistics.js` | 255 | 纯函数：积分器、仰角求解、遮挡、伤害公式、弹种表。**无依赖，是全项目最干净的一层** |
| `referee/rules.js` | **1769** | 常量表 + 地图生成 + 视野/LOS + `Game`（移动/开火/弹道推进/经济/生产/科技/分配/模式/VP/计分/**协议编解码**/确定性哈希），`Game` 一个类 **56 个方法** |
| `referee/referee.js` | 381 | driver（模拟子进程）+ 时序策略 + 红牌策略 + 计分汇总 + 回放格式 + 排名 |
| `referee/tournament.js` | 179 | 赛程编排 + 表格/CSV 输出 |
| `referee/match.js` | 329 | Canvas 渲染 + DOM 交互（读全局 `WoDRef`） |
| `referee/bots/*` | 364 | 两个纯 `init/decide` Bot |
| `test/*` (4 文件) | 1310 | 白盒单测 |

**单文件承载 6 类职责**（地图 / 物理 / 规则 / 协议 / 计分 / 确定性）的代价是具体的：改协议要动引擎文件，改计分要动引擎文件，路由一处失败就得读 1700 行。

### 5.2 依赖关系

```
ballistics.js  ←(唯一干净依赖)─  rules.js  ←  referee.js  ←  tournament.js
                                   ↑            ↑
                                match.js ───────┘   (浏览器全局 WoDRef，靠 <script> 顺序加载)
                                   ↑
                                 bots（纯函数，无依赖）
```

方向本身是对的（无环、单向）。问题在三处**边界泄漏**：

1. **协议进引擎**：`Game.encodeHello/encodeTick/decode` 与模拟耦合。512² 要换编码（RLE/base64）、可能要发增量 diff，这些改动都得在规则文件里做。**引擎不该知道「一行 JSON」这件事。**
2. **计分进引擎**：`computeCards/checkEnd` 在 `Game` 上。计分口径是赛事规则、会独立演进（BT/Elo、权重调整），现在改权重就要动引擎。
3. **时序/判罚进 driver**：`decideSeat/applyStrikes/tickOnce` 把「多长算超时」「几次算红牌」写成流程，而这两条在 `Plan_Beta` 里仍标着待定。

另外：**2 人假设写死在数组下标里**（`[0,1]`、`orders[0]`、`units.filter(u=>u.side===0)`），`Game(4)` 直接抛错。1v1 是当前需求，但这条假设已经渗透到协议、计分、记录、回放，未来扩展的改造成本不是「加个循环」。

### 5.3 可维护性

| 项 | 现状 | 影响 |
|---|---|---|
| 类型 | 无 TS、无 JSDoc 类型标注 | `state.units[].mode`、`sides[s].queue` 这类结构全靠读代码 |
| 模块系统 | UMD 双模（`module.exports` / `root.WoDRef`）+ 全局命名空间 + 手工加载顺序 | Node 与浏览器两条路径都要维护；`if (!B) throw` 只是兜底 |
| 静态检查 | `npm run check` = 12 条 `node --check`（纯语法） | 无 lint、无类型检查、无未使用变量检测 |
| CI | **无**（外层与 MVP 都没有 CI 配置） | 全绿是「本地跑过」，不是「每次提交都跑」 |
| 覆盖率工具 | 仓库内无（本轮用 `NODE_V8_COVERAGE` 临时测） | 覆盖率不可持续观测 |
| 命名债 | `carrier(s) { return this.mothership(s); }`（兼容旧名） | `match_test` 用 `carrier(1).hp=0` 杀母舰，**读代码的人会以为是运载舰** |
| 常量硬编码 | `GRID=64, CELL=12, M_PER_CELL=40` 是模块常量 | 换尺度必须改源码；数值平衡只在这组尺度下成立 |

### 5.4 扩展性

| 扩展点 | 现状 | 需要什么 |
|---|---|---|
| 64² → 512² | 遇三重硬墙：`hello` 1.9 MB > `MAX_LINE` 64 KB；`visionGrid` ≈20 ms/tick（预算 50 ms）；回放体积线性膨胀 | 编码压缩、视野增量化/按需查询、帧抽样策略、尺度重标定 |
| 世界尺度 | `1 格 = 12 px = 40 m`，世界 2.56 km；单位速度 3.2 格/s、射程 3.2 格 | 512² 时要么世界变 20 km（600 tick 走不完），要么格变小（射程/视野/伤害全要重标定）。**这不是调参，是重新设计** |
| 多人 | `Game(4)` 抛错 | 协议、计分、记录、回放全线改造 |
| 跨语言确定性 | `frameHashes` = 对 `JSON.stringify(frame)` 做 FNV-1a | JS 与 Go 的浮点格式化、键序、数字指数写法都不同，**逐字节相等不是自动成立的**，需要规范化序列化规范 |
| 反作弊 | 同进程，规则表可变 | 子进程 + 白名单 + 资源限制（`Plan_Beta` 已规划，MVP 未做） |

| 级别 | 风险 | 证据 |
|---|---|---|
| **严重** | 进程内 Bot 可绕过信息集、可改共享规则表，且零故障 | §3.5 两个实验 |

## 7. 缺失环节（主项目必需、MVP 完全没有）

1. **进程/沙箱**：子进程、STDIN/STDOUT、超时 kill、内存/CPU 限制、panic 兜底；
2. **静态白名单**：AST import 检查（Go 侧）；
3. **512² 地图与编码**：RLE/base64、地图哈希、`mapAttempt` 语义在大图上的复核；
4. **选手包流水线**：`workspace_manifest.json` + 逐字节一致的打包与校验；
5. **评测调度**：并发局数、机器负载记录、`CONDITIONS.md`（复现条件）；
6. **排行榜**：BT 全池拟合 / Elo；
7. **回放消费端**：Three.js 播放器或等价工具（现在只有 JSON + 简易观战页）；
8. **规则/地图版本管理**：`rulesHash` 之外的「赛季规则包」与旧 Bot 迁移策略；
9. **CI 与质量门槛**：lint、覆盖率门槛、性能预算测试；
10. **反作弊审计**：作弊检测、日志取证、重放复核的自动化。

## 8. 迁移前必须补充 / 调整的事项

### P0（阻断项，不做完不应动工）

1. **冻结基线并止血版本控制**：给 MVP 打 tag（`v0.9-baseline`）；把真正要交付的代码纳入可交付仓库（或明确「MVP 目录即交付物」并加异地备份）；删除 `_archive_skeleton/`（两套引擎并存必然漂移，`arena/core.js` 与 `rules.js` 已经是两套规则）。
2. **定义 golden trace 夹具**：N 组 `(seed, tickLimit, vision, orderLog, 每 tick 协议行 SHA1, frameHashes, result)`，以 JSON 行落盘。**这是 Go 版唯一可信的对拍基准**，也是「MVP 作预言机」这条路线成立的前提。
3. **定死规范化序列化规范**：字段顺序、浮点格式（几位有效数字/是否用最短往返）、UTF-8 字节计长、NaN/Infinity 处理、时间字段不进哈希。否则跨语言哈希永远对不齐。
4. **把协议从引擎里拆出来**（哪怕是 JS 内的逻辑分层）：`encode/decode/hello/tick/end` + 地图编码独立成模块；同时定 512² 的编码方案与单行体积上限（当前 `hello` 会直接超 `MAX_LINE` 30 倍）。
5. **尺度参数化 + 512² 重标定方案**：`GRID/CELL/M_PER_CELL` 变成可配置；明确世界尺寸、射程、视野、速度、`tickLimit` 的换算；重跑并重记平衡表（现有数值只对 1 格 = 40 m 成立）。
6. **反作弊边界先立规矩**：明确「同进程 = 不可信」，Go 版必须子进程 + 白名单 + 规则表只读；MVP 阶段至少在 README/`CONDITIONS.md` 写清这条已知限制，避免被当成「已验证隔离」。

### P1（正式赛前必须有）

1. 补齐未覆盖分支的用例：`carveCorridor`/兜底地图、`pointVisible`（炮弹可见）、`queue full`、`bad attack target`、`verifyDeterminism` 三条失败分支、`step()` 造炮二次校验、`strikeMode:'cumulative'`。
2. 把「射程门」用例改到 **4 格**（3.4–5.5 格可观测带内），否则删掉射程判断也不会报警。
3. 引入 CI（跑 `npm test` + `npm run check`）、lint、覆盖率门槛（c8）；把本轮临时用的 V8 覆盖率流程固化成脚本。
4. 性能预算测试：单 tick 上限、`visionGrid` 成本、`hello/tick` 体积、回放体积上限；512² 落地前先有基线。
5. 平衡回归基准带：固定 8–10 个 seed，断言「分数落在区间内」而非精确值，避免「Tactical 5:1 但总分更低」这类无法判定对错的结果反复出现。
6. 时间口径统一：`算力表现` 改 CPU 时间或确定性度量；把忙等用例改为注入假时钟。

### P2（可与上线并行）

1. 文档一致性：`MVP_plan` §17 的 `GRID=128`、G1/G5 已废弃、`web_smoke` 断言数、`carrier()` 别名；
2. 类型化（JSDoc 或直接转 TS）以降低 1769 行文件的阅读成本；
3. `visionGrid` 增量化（只重算变化区域）或改为按需查询，为 512² 铺路；
4. 测试框架迁移到 `node:test`（零依赖，仍符合「零第三方依赖」约束），拿到 `--experimental-test-coverage` 与单测过滤。

## 9. 可行性结论

**判定：有条件可行（Conditional Go）——「重写式迁移」，不是「搬代码」。**

可以把 MVP 作为主项目底座的部分：

| 资产 | 是否可迁移 | 说明 |
|---|---|---|
| 协议形状（hello/tick/end、动作表、语义非法 vs 结构性错误两层校验） | ✅ 直接可用 | 已经是`Plan_Beta` 的落地形态，只需换编码 |
| 时序模型（50/120 ms、指令晚 1 tick、延迟不进状态） | ✅ 直接可用 | 设计正确，只需与 `Plan_Beta` 的 60 ms 口径收敛 |
| 计分卡与判定链 | ✅ 直接可用 | 权重、区分度、赢局低分都有断言 |
| 确定性方法（orderLog + frameHashes + 篡改检测 + 规则指纹） | ✅ 方法论可用 | 实现要按 Go 重写，并补规范化序列化 |
| 数值表 / 平衡表 | ⚠️ 需重标定 | 只对 64² × 40 m/格成立 |
| 322 条测试 | ❌ 大部分不可迁移 | 白盒改内部字段；应转成「行为规约表 + golden trace」 |
| JS 实现 | ❌ 不迁移 | 主项目是 Go；即便留在 JS，也需先拆 5 层 + 冻结规则表 + 进程隔离，工作量约等于重写 60% |

**为什么不能直接拿 MVP 当主项目内核**（三条硬理由）：

1. **隔离**：比赛的第一性要求是「Bot 看不到不该看的东西、改不了不该改的东西」。MVP 的隔离只在消息层成立，实测可被原型 patch 与规则表篡改绕过，且零故障。
2. **尺度**：512² 触碰三处硬约束（`hello` 体积、视野计算、回放体积），这些都在 `rules.js` 内部，且与协议、渲染、回放耦合。改造成本高于重写。
3. **边界**：1769 行单类同时是「引擎 + 协议 + 计分 + 地图」，任何一处演进都要动同一个文件；而主项目要长期演进规则、评分、赛制。

**建议的执行顺序**：

```
冻结 v0.9 基线 → 产出 golden trace（3–5 组）→ 写规范化序列化规范
   → Go 实现协议层 + 地图生成 + 弹道（先做能对拍的最小闭环）
   → 用 trace 逐字节对拍（不一致就回查，不看「看起来对」）
   → 补进程隔离 + AST 白名单 + 资源限制 → 再补计分/赛制/排行榜
```

只有在「golden trace 对拍全绿」之后，才建议把 MVP 的 JS 代码降级为「历史参考实现」，并停止在其上继续加规则——否则两套实现会持续漂移，而漂移的代价在赛事里是「同一 Bot 两种成绩」。
