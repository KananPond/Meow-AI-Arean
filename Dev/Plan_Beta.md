## 1. 正式版目标

### 1.1 不变目标

- 本地 AI 算法与叙事双轨社区赛。
- 红蓝 1v1，无头评测，选手提交 Bot 代码。
- 引擎与 Bot 交付链最终使用 Go 标准库，保持零第三方运行时依赖。
- 同一 `seed + 规则配置 + orderLog` 必须能复现同一局；计分中的机器相关项单独归一，不污染模拟确定性。
- 胜负标签与多领域加权总分是两个独立信号：前者决定单局胜负，后者用于跨局质量评价。

### 1.2 本轮非目标

- 不在基线快照上继续加功能；规则演进在 `MVP/` 上做，快照按版本重出。
- 不直接照搬 MVP 的 UMD、同进程 driver、`Game` God Class 或 JS 哈希实现。
- 不在迁移准备阶段完成 Go 引擎实现。
- 不恢复已移除的人类可玩版。
- 不把 BT/Elo、叙事榜和 Three.js 回放列为 Go 引擎迁移的前置阻断项；它们属于赛制与运营层。

## 2. 基线快照采纳的 v1.0 规则基线

以下决策优先于 `Plan_Alpha.md` 和旧版 `Plan_Beta.md`。

| 项 | v1.0 决策 |
|---|---|
| 对抗形式 | 2 方 1v1；拒绝把多方对局静默当成 1v1 |
| 地图 | 256×256，1 格 = 10 m，世界 2.56 km |
| 地图生成器 | `minecraft` 为默认；`geomorphic` 为可选；两者共用对称、点位和连通性收尾 |
| 逻辑节奏 | 20 tick/s，即 `TICK_MS = 50`；单局 `1200 tick`（60 s） |
| 决策预算 | `DECIDE_MS = 120`；`INIT_MS = 2000` |
| 指令延迟 | 固定 `ORDER_LATENCY = 1 tick`，不随 Bot 思考耗时变化 |
| 红牌 | **连续 3 次故障**出局；累计模式只作为未来赛制选项，不是 v1.0 默认 |
| 初始资源与兵力 | 双方固定 500 CU；母舰 + 2 LAV |
| 资源模型 | 单 CU；Salvager 在资源点站桩采集；v1.0 不采用 CU/RU 双资源 |
| 母舰机制 | 生产 / 攻击 / 研究 / 移动四项百分比分配，按 5%/tick 过渡 |
| 科技 | 火力、装甲两条线性树；机动、工业两条交叉树 |
| 弹道 | 二次阻力 + 重力，RK4 积分；伤害由落速、弹种、装甲与克制决定 |
| 高地 | 不采用固定 +25% 伤害 / +20% 射程；高地收益由弹道物理自然产生 |
| 视野 | 引擎默认关闭以兼容冻结基线；正式比赛配置必须显式声明开/关。开启时只改变信息集，不改变模拟 |
| 单位模式 | `obey / neutral / aggressive`；SCOUT、SALVAGER 退化为服从 |
| 胜负链 | 母舰被毁 → VP → KD 差 → 母舰 HP 比例 → 平局 |
| 八领域权重 | VP 25%、歼敌 15%、保存兵力 15%、母舰完整度 15%、KD 10%、战场控制 5%、推进效率 5%、算力表现 10% |

### 2.1 有意偏离旧计划的决策

这些不是漏做，而是当前基线：

- 旧计划的 10 TPS 被 20 TPS 取代；单局 tick 数在 v1.1 从 600 拉回 **1200**（20 TPS × 1200 = 60 s 逻辑时长），配合移动时间基准修正（`applyMove` 由 0.1 s/tick 改回 `TICK_MS/1000`）。
- 旧计划的 60ms 死线被 120ms 决策预算取代；但正式版必须保留进程级 deadline、kill 与回复丢弃能力。
- 旧计划的随机初始兵力被固定初始配置取代；随机性主要来自地图。
- 原作式母舰四子系统被四项百分比分配取代。
- 固定高地加成被外弹道模型取代。
- 单 CU 站桩采集取代 CU/RU 双资源和运输线。

## 3. 正式协议契约

### 3.1 消息流

正式 Go 版必须让以下消息全部走真实 UTF-8、行分隔 JSON 序列化链路，禁止同进程对象直传：

1. `hello`：开局一次，含协议版本、规则指纹、规则常量、地图、生成器和时序。
2. `tick`：每 tick 一次，向 Bot 提供当前信息集。
3. `actions`：每 tick 一次，Bot 返回动作数组。
4. `end`：结算一次，含胜负、判定层级、完整计分卡和叙事榜所需数据。

### 3.2 线体积

- 所有消息均不得包含未转义换行。
- `tick` 与 `actions`：**≤ 64 KiB**。
- `hello`：**≤ 128 KiB**（v1.1；256² 实测约 110 KB）。
- 基线快照在 256² 下的 `hello` 实测约 110 KB；512² 前必须通过更强压缩、分层编码或合规分块把 `hello` 收敛到 128 KB 以内，不能用继续放宽阈值掩盖。
- `end` 目标 ≤ 256 KiB；超过时叙事数据必须采用索引、压缩或附加文件。

### 3.3 协议 schema

P1 阶段必须提供机器可读契约，至少一种：

- Go DTO + 固定字段顺序的编码器；或
- JSON Schema + 独立一致性测试。

schema 必须覆盖：字段名称、类型、可选性、数组形状、枚举、坐标单位、编码方式、错误行为和版本迁移。

### 3.4 时序与超时语义

- `hello` 不计入单 tick 决策预算，独立使用 `INIT_MS = 2000ms`。
- 每个 `tick` 的计时窗口从引擎写出 `tick` 行开始，到读完整 `actions` 行结束。
- 超时、坏 JSON、非法动作结构、进程崩溃或进程被杀都记一次故障。
- 连续 3 次故障判故障出局；故障 tick 的动作列表视为空。
- 超时的回复不得进入当前或后续 tick；`ORDER_LATENCY = 1` 是协议保证，不得受机器负载影响。
- 换边必须重启 Bot 进程，禁止跨局保留内存状态。

### 3.5 开发用时与强制收卷

开发阶段的“比赛时间”与单局 `DECIDE_MS` 是两套计时，不得混用：

- 选手包必须包含 `workspace/clock.py`，供模型随时查看开发已用时间、目标时间和强制收卷时间。
- 组织方使用 `开赛.py` 开赛、暂停、恢复和收卷；权威记录写入 `赛务记录.json`，`clock.py` 是选手侧展示，不作为最终审计依据。
- 默认赛程：90 分钟为目标完成时间，120 分钟为强制收卷；到点后即使仍可留档，也必须标记 `accepted=false`。
- 收卷对象是 `workspace/submission/decide.go`；强制收卷时复制到 `<选手目录>/submissions/decide.go`，记录 SHA-256、字节数、用时、accepted 和缺失状态。
- 未找到 `decide.go` 也必须生成收卷记录，且 `accepted=false`、`missing_submission=true`。
- 暂停/恢复必须写入赛务记录；暂停期间不增长已用时间，恢复后接续原计时。
- 选手不得修改 `clock.py` 或赛务记录；组织方重置计时时必须保留重开、暂停和收卷历史。

当前工具实现见：

- 选手侧：`workspace/clock.py`
- 组织侧：`开赛.py`

## 4. Go 目标架构

正式实现按以下边界组织；本轮只冻结边界，不写实现。

```text
protocol/
  消息 DTO、版本、schema、规范化序列化、RLE/base64 地图编解码
  禁止依赖 engine / io / scoring

engine/
  mapgen / terrain / movement / ballistics / vision / economy / combat
  end-condition / replay-input
  纯确定性，不读墙钟，不启动进程，不做 IO

scoring/
  八领域归一化、权重、算力域归一化、计分卡输出
  只消费 engine 的确定性结果与明确标注的时序测量值

io/
  os/exec、stdin/stdout、deadline、kill、换边重启、结果归档
  唯一允许接触外部进程、墙钟和文件系统的一侧
```

### 4.1 依赖规则

- 依赖只能向内：`cmd / tournament → io / scoring → engine → protocol` 所需的稳定类型；不得反向依赖。
- `engine` 必须能在无文件系统、无网络、无外部进程的环境下跑 golden trace。
- `terrain.go` 与 `ballistics.go` 的公开计算函数由引擎和选手包共用同一份源码，禁止复制公式。
- 所有随机性只允许来自显式 seed；不得从时间、进程 ID 或全局状态取随机数。

## 5. 确定性与对拍规范

### 5.1 模拟确定性

Go 候选实现必须做到：

- 同一 `seed + generator + tickLimit + vision + orderLog` 得到同一单位状态、事件序列、胜负层级和除算力域外的计分卡。
- 浮点实现必须使用 IEEE 754 `float64`；关键输入、排序、遍历顺序和舍入口径必须固定。
- 禁止依赖 JSON map 迭代序、对象插入序或语言默认格式化结果。

### 5.2 哈希与 golden trace

基线快照的 `fnv1a(JSON.stringify(...))` 是 JS 内部回归工具，**不是跨语言契约**。Go 版不得直接照搬。

P1 必须产出至少 3 组、建议 5 组 golden trace：

- 覆盖默认 `minecraft` 与可选 `geomorphic`。
- 覆盖短局、满 1200 tick 局、斩舰局、VP/KD/HP 判定路径。
- 同 seed、同 orderLog，对拍逐 tick 单位、炮弹、事件、胜负和确定性计分域。

trace 比较规则：

- 状态字段按完全相等或事先定义的定点容差比较。
- 算力表现域单独比较统计口径，不参与模拟确定性判定。
- JS oracle 哈希只作生成端自检；跨语言对拍以规范化 trace 为准。

### 5.3 算力表现归一

第 8 领域保留“算力表现”目标，但正式排名不允许直接使用未归一墙钟毫秒数。

v1.0 采用：

- 引擎记录每次决策耗时、超时和故障。
- 每台评测机先运行固定基准 Bot，得到机器校准因子。
- 第 8 领域按“预算余量 / 基准校准”归一；机器信息写入 `CONDITIONS.md`。
- golden trace 的算力域只验证字段存在、单位和统计口径，不验证数值复现。

## 6. 测试与验收门禁

### 6.1 迁移准备门禁

1. 基线快照对应提交固定为 `288db07f164bc6c680a2d878c47153804d3fdcab`（tag `baseline/288db07`）。
2. `npm run check` 通过。
3. `npm test` 10/10 通过。
4. 覆盖率失败被明确归类为“快照预言机采集/性能门槛问题”，不得再表述为规则测试失败。
5. 本文、根 README、`Dev/README.md` 与 Docs 索引一致。

### 6.2 Go 候选实现门禁

未全部满足不得替换快照 oracle：

- 能加载 schema 并拒绝未知协议版本。
- `hello/tick/actions/end` 全部经过真实序列化。
- 独立进程、死循环 kill、非法 import 拦截、换边重启、连续 3 红牌均有自动化测试。
- golden trace 对拍通过。
- 256² 下 `hello/tick/actions` 满足 §3.2。
- 8–10 个 seed 的平衡回归完成，权重和计分卡格式稳定。
- 覆盖率报告不依赖修改基线快照；行覆盖之外至少包含分支覆盖。
- 正式比赛配置、地图生成器、视野开关、seed、结果和随机源全部可复现。

**当前口径（2026-11-12）**：上述门禁未全部满足。正式赛使用快照 oracle 引擎，`war_of_desert/` 只落地了赛制与执行链；在 Go 引擎通过全部门禁前，不得宣称可替代 oracle。

## 8. 已知风险

| 风险 | 处理 |
|---|---|
| 基线快照的 `npm run coverage` 在插桩下触发性能断言 | 不改快照代码；P1 建立独立采集/报告链，并将墙钟断言排除出覆盖率路径 |
| `hello` 当前约 110 KB | v1.1 契约 ≤128 KiB；512² 前先解决编码/分块，再开放外部选手 |
| 同进程 MVP 无法证明进程隔离 | 以进程级 kill、死循环、非法 import、换边状态泄漏测试作为 Go 版硬门禁 |
| 跨语言浮点差异可能改变命中边界 | golden trace 定义定点或容差；关键路径减少非确定性遍历 |
| 计分卡含算力域 | 模拟确定性与排名分数分离；算力域按基准 Bot 校准 |

## 12. 变更规则

- 修改规则语义：必须先更新本文并说明对 golden trace 的影响。
- 修改协议：必须先更新 schema，再更新实现与测试。
- 修改基线快照：禁止（快照是只读字节）。规则修订在 `MVP/` 上做，按 `ORACLE.md` §2 的流程新出快照 + 新 `rulesHash`。
- 新增功能：先判断属于 engine、protocol、scoring、io 还是赛制运营层，再进入对应阶段；禁止把赛制功能塞进引擎核心。
